# 专利点 3：基于响应帧等待的应答匹配方法

> 对应《专利思路.md》第一部分第 3 点。**申请优先级：强，建议与第 2 点合并为"串口通信容错与应答匹配方法"，或作为其从属权利要求。**

## 撰写边界

- 报文号本身是设备协议内容，权利要求中表述为"期望响应特征集合"。
- 发明点在"待决命令对象 + 特征匹配 + 超时 + 对象同一性防误杀"的机制，不涉及协议字节。

## 一、技术问题

串口是**无事务概念的字节流**：主站发完一条命令后，缓冲区里可能同时混着上一轮命令的迟到响应、设备主动上送的数据帧和本轮的响应。Qt 原版的对话框采用"**固定延时盲读**"：发送命令后延时 666ms/1000ms 再去解析缓冲——设备响应慢时，读到的就是**上一轮旧数据**，导致界面显示旧值（参数对话框显示与设备实际状态不符）。命令与响应之间没有一一对应的绑定关系，是问题根源。

## 二、创新点

1. **待决命令对象**：发送命令时创建一个"待决命令"对象，携带本命令的标识（报文号）与**期望响应特征集合**（期望报文号集合 和/或 短应答成功标志），挂在通信管理器的唯一待决槽位上；此后所有接收事件都先与该对象匹配。

2. **多候选响应号匹配**：期望特征用**集合**而非单值表达——同一条命令允许对应多种可能的响应报文号（如校准命令：Qt 假定设备回 41 号帧，设备实际回 39 号帧 `[通道号, 0x55]`），任一命中即匹配成功，并据响应帧内容判定成功/失败。

3. **对象同一性防误杀**：定时器回调与完成/失败回调在生效前都校验"当前待决命令是否还是本对象"——残留的旧定时器不会误杀后发的新命令（单线程事件循环下，旧回调晚到是常态）。

4. **命令互斥**：同一时刻只允许一条待决命令；已有待决命令或正在进行连接/获取会话时，新命令被拒绝并提示——从根上杜绝两条命令响应互相串扰。

5. **短应答的上下文化成功判定**：应用类（下载/设置）命令期待短应答为成功标志（`expectE5`），读取类命令期待数据帧——"什么算成功"由命令对象声明，而不是接收端写死。

## 三、具体实现方式

### 3.1 待决命令对象结构

```
pendingCommand = {
  nr,            // 本命令报文号（日志用）
  expectNrs,     // 期望响应报文号集合（多候选），null 表示只期待短应答
  expectE5,      // true = 收到短应答即判成功（应用/设置类命令）
  timer,         // 本命令的 3333ms 超时定时器
  resolve(f),    // 成功出口：先校验对象同一性，再清定时器、清空槽位、返回响应
  reject(err),   // 失败出口：同上，返回错误
}
```

### 3.2 发送流程（Promise 化）

1. 前置校验：串口已连接、无进行中的会话、无已存在的待决命令，三者任一不满足即拒绝；
2. 组装帧并写入串口；
3. 创建待决命令对象存入全局唯一槽位，启动 3333ms 超时定时器（可被命令选项覆盖）；
4. 返回 Promise——界面层 `await` 该 Promise，成功拿到响应帧后解析刷新，失败（超时/发送失败/串口断开）拿到错误并提示。

### 3.3 接收端匹配（在全局帧分发点完成）

```
收到数据帧：
  ① 登记注册表 + 回主站应答（与匹配无关的常规动作）
  ② 若存在待决命令且该帧报文号 ∈ 期望集合 → 以该帧解决待决命令
  ③ 其余意外帧不解决命令，等超时（与源程序"对话框只按响应号解析"一致）
收到短应答：
  若待决命令声明 expectE5 → 以短应答解决待决命令（成功）
```

### 3.4 对象同一性防误杀（关键代码语义）

```
resolve: (f) => {
  if (pendingCommand !== cmd) return;   // 已被新命令取代的旧回调 → 直接丢弃
  clearTimeout(cmd.timer);              // 只清自己的定时器
  pendingCommand = null;
  resolve(f);
}
// 定时器回调同样先校验 pendingCommand === cmd 再 reject
```

### 3.5 多候选匹配实例（校准命令）

- 设备对校准命令（38 号）实际回 **39 号帧** `[通道号, 0x55]`（0x55 为成功状态字节），而 Qt 源程序假定回 41 号——Qt 版界面因此永远看不出校准成功。
- 本方案：校准命令声明 `expectNrs: [39, 41]` + `expectE5: true`，设备回 39 即匹配成功，并按状态字节判定；回 41 或短应答亦兼容。

## 四、与 C++（Qt 原版）方式的不同点

| 维度 | Qt 原版（固定延时盲读） | 本方案（响应帧等待匹配） |
|---|---|---|
| 触发方式 | 发送后固定延时 666/1000ms 解析缓冲 | 事件驱动：响应帧（或短应答）到达即匹配解决 |
| 命令-响应绑定 | 无绑定，解析的是"缓冲里恰好有的字节" | 待决命令对象 + 期望特征集合，严格一一对应 |
| 设备响应慢 | 读到上一轮旧数据，界面误显示旧值 | 等待期间不解析旧数据；超时 3333ms 明确报错 |
| 响应号假设错误 | 只按假定的响应号解析，设备实际回别的号 → 永远"没反应" | 多候选集合（如 [39, 41]），任一命中即成功 |
| 并发命令 | 无互斥，两条命令响应可串扰 | 命令互斥，同时只允许一条待决命令 |
| 成功判定 | 依赖解析结果，界面看不出校准是否成功 | 短应答/状态字节均可声明为成功标志，成功可判定 |
| 定时器误触发 | 定时器与本轮命令无身份绑定 | 对象同一性校验，旧定时器回调自动失效 |

## 五、技术效果

- **杜绝旧数据误显示**：命令-响应严格一一对应，慢响应、乱序响应、意外帧都不会污染界面。
- 校准等命令的**成功/失败可判定**（Qt 版界面永远看不出校准成功）。
- 每一条对话框命令都有明确的完成/超时/失败三种结局，界面可精确提示（"等待响应超时（报文 X，期待 Y）"）。

## 六、权利要求要点建议

**权利要求（方法，可作为第 2 点主权利要求的从属项，或独立成权利要求）**：一种串口通信的命令-响应匹配方法，其特征在于：
- 主站发送命令时，创建携带命令标识与期望响应特征集合（期望响应报文号集合 和/或 短应答成功标志）的待决命令对象，并启动响应超时定时器；
- 接收端收到数据帧时，若该帧报文号属于期望响应报文号集合，则以该帧匹配成功并返回；收到短应答时，若命令声明短应答成功标志，则以短应答匹配成功；
- 超时定时器到期仍未匹配，则返回超时错误；
- 所述待决命令对象与定时器回调之间以对象同一性校验关联，被新命令取代的旧回调自动失效；
- 同一时刻仅允许存在一条待决命令。

**从属权利要求方向**：期望响应报文号集合含多个候选报文号（命令实际响应号与假定响应号不同时兼容）；超时时长 3333ms；匹配成功后按响应帧内容判定业务成功/失败；串口断开时待决命令立即以错误解决。
