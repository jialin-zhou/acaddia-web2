# 专利点 4：静默窗口 + 应答字节消歧的串口流式解帧方法

> 对应《专利思路.md》第一部分第 4 点。**申请优先级：较强。注意——100ms 静默窗口机制 Qt 原版已有（现有技术），本点的发明性在于"以静默窗口为粒度区分帧前缀与独立短应答"的完整上下文分流规则 + Web 环境实现，建议作从属权利要求，或并入第 2 点。**

## 撰写边界

- 帧格式、前缀字节、短应答字节本身是协议内容，权利要求中表述为"帧前缀应答字节""独立短应答""完整数据帧"。
- 发明点 = 时间上下文消歧规则集 + 上下文分流规则集，**不主张**静默窗口机制本身。

## 一、技术问题

同一字节 E5 在协议中是**双义的**：

- 作为**数据帧前缀**：设备上送数据帧时为 `E5 68 L L 68 …校验和 16`；
- 作为**独立短应答**：设备对命令的"已收到"确认，就是单个字节 E5。

从字节流角度看两者无法区分。若把每个 E5 都当短应答，数据帧就被拆坏；若都当前缀，则"设备仅确认、无数据"的场景永远等不到帧——这正是 Qt 获取流程卡死的原因之一（专利点 2 的缺陷与本消歧缺失互为因果）。

## 二、创新点

1. **以静默窗口为消歧粒度**：不逐字节判断，而是把设备一次静默间隔内到达的全部字节聚为一批（100ms 静默窗口），以"批内结构"作判断依据——`E5 后紧跟完整数据帧` 即前缀，`独立成批的裸 E5` 即短应答。**窗口本身是现有技术（Qt 亦有），以窗口为粒度做双义消歧的规则集是本点的发明部分。**

2. **前缀判定规则**：同一窗口内短应答字节后**紧邻**通过头部、长度、帧尾、校验和四项校验的完整数据帧 → 判定为帧前缀，按数据帧正常处理（不触发任何应答逻辑）。

3. **独立短应答的三路上下文分流**：独立成批的短应答按会话上下文分三路——
   - **待决命令期**：命令声明短应答为成功标志 → 命令成功（与专利点 3 联动）；
   - **连接期**：计错误、重发链首命令（与专利点 2 联动）；
   - **获取期**：判定"设备已确认且无数据可回"，正常结束会话（专利点 2 的收敛出口）。
   空闲状态收到的孤立短应答则忽略并记录。

4. **独立令牌输出的流式解帧**：解帧器把短应答、完整帧、垃圾字节作为**独立令牌分别输出**，且支持一批多帧——较 Qt"要求帧带前缀、一次只解析一帧"的解析器行为等价但更健壮。

5. **容错跳过规则**：帧头校验（长度字段成对、帧尾存在）、校验和校验失败时，跳过该起始字节继续搜索后续帧；无法解析的字节标记为垃圾并记录日志——异常字节不会卡死解析。

## 三、具体实现方式

### 3.1 静默窗口聚批（接收循环）

```
读取循环：
  chunk = await 串口读取()
  batch.push(...chunk)                 // 收字节入批
  重置 100ms 静默定时器                // 每次新字节都重置
  定时器到期（100ms 无新字节）→ processBatch(batch)；batch 清空
```

100ms 与 Qt 定时器（m_timer11）同值；定时器随字节到达不断重置，实现"按静默间隔切批"。

### 3.2 流式解帧器（令牌化）

```
解帧器对每批字节：
  字节 == E5      → 输出 { type: ack_e5 }         // 短应答令牌（不预判双义）
  字节 == A2      → 输出 { type: ack_a2 }         // 回显应答令牌
  字节 == 68      → 校验 68 L L 68 头（L 成对）
                   → 校验帧尾 16
                   → 校验和 = 数据块累加 & 0xFF，不符 → 跳过该 68 继续搜索
                   → 输出 { type: data, telegramNr, dataBlock, payload, raw }
  其他字节        → 垃圾字节，继续搜索
```

### 3.3 批内消歧与分流规则（核心规则集）

```
processBatch(batch)：
  frames = 解帧器(batch)
  顺序处理每个令牌：
    data      → 常规动作（登记注册表 + 回主站应答）+ 驱动状态机/待决命令匹配
    ack_e5    → 若下一令牌为 data（同批内紧跟完整帧）→ 判定为帧前缀，跳过
                （数据帧本身已在后一条正常处理，不触发应答逻辑）
                否则（独立短应答）→ 按上下文三路分流：
                    待决命令声明期待短应答 → 命令成功
                    连接期 → 计错误 + 重发链首命令
                    获取期 → 置数据结束标志 + 正常结束会话
                    空闲   → 忽略并记录
    ack_a2    → 连接期 → 计错误 + 重发链首命令；获取期 → 忽略（仅记录）
    junk      → 记录日志，继续
```

### 3.4 与相关专利点的联动

- 分流规则第二路（连接期计错重发）、第三路（获取期收敛）即专利点 2 状态机的输入事件来源；
- 第一路（待决命令成功）即专利点 3 的匹配事件来源；
- 三者共同构成"时间上下文消歧 → 上下文分流 → 有界收敛"的完整闭环，可作为一项从属权利要求整体主张。

## 四、与 C++（Qt 原版）方式的不同点

| 维度 | Qt 原版 | 本方案 |
|---|---|---|
| 聚批机制 | 已有 100ms 静默窗口（收字节入 RXDAT，m_timer11 定时整批解析） | 相同（**现有技术，不主张**） |
| 解析器形态 | 要求数据帧带 E5 前缀，一次只解析一帧 | E5 与帧**分开输出独立令牌**，支持一批多帧，行为等价且更健壮 |
| E5 双义处理 | 无消歧规则：E5 只作为帧前缀的一部分存在，独立的裸 E5 落空 | 批内规则：E5 后紧跟完整帧 → 前缀；独立成批 → 短应答 |
| 独立短应答的去向 | 获取期收到独立 E5：**无任何处理**，状态机停在等待末帧 | 按上下文三路分流（待决命令/连接期/获取期），各有确定动作 |
| 校验失败/垃圾字节 | 解析中断风险高 | 校验失败跳过该起始字节继续搜帧；垃圾字节记录后继续 |

## 五、技术效果

- **不加协议字节、不改协议**，靠时间上下文完成双义消歧。
- "设备仅确认、无数据"的真实工况被正确识别——获取流程不再卡死（配合专利点 2 形成正常收敛出口）。
- 应用/设置类命令的成功判定可靠（独立短应答 = 成功，配合专利点 3）。
- 异常字节（校验失败、垃圾）不会中断解帧，流式解析持续可用。

## 六、权利要求要点建议

**权利要求（从属权利要求，依附于状态机主权利要求，或并入第 2+3 点组合）**：一种串口流式解帧的应答字节消歧方法，其特征在于：
- 接收端按预设静默间隔（100ms）将到达字节聚为批次；
- 对每批字节进行令牌化解帧，分别输出短应答、回显应答、数据帧与无法解析字节的令牌；
- 当短应答令牌后紧跟完整数据帧令牌时，判定该短应答为帧前缀，仅按数据帧处理；
- 当短应答令牌独立成批时，判定为独立短应答，并按当前会话上下文分流处理：存在待决命令且命令声明短应答为成功标志时判为命令成功；连接会话中计为错误并重发链首命令；数据获取会话中置数据结束标志并正常结束会话；空闲状态忽略。

**从属权利要求方向**：帧校验包括头部成对校验、帧尾校验与累加校验和校验，校验失败跳过该起始字节继续搜索；回显应答按会话上下文分别处理（连接期计错重发、获取期忽略）。
